# Agent 设计

所有 Agent 统一通过 `backend/app/core/llm.py:get_llm()` 使用 OpenAI-compatible LLM，不允许独立初始化模型。

## Prompt 版本

Agent 的职责、System Prompt、模型、Memory、知识访问、审批与并发配置按不可变版本保存。管理员可创建草稿，并从 AI 员工页进入 Challenger 评测；只有在匹配生产基线的评测通过门禁后才允许发布。旧的直接配置、发布和回滚 API 已弃用，有状态变更时返回 `409` 并写入阻断审计。评测驱动的回滚会创建新的恢复版本而不改写历史，所有动作写入审计日志。

## 路由

- 用户显式 `agent_id`：最高优先级，不存在时返回 404，不静默降级。
- 文本明确提及角色：置信度 0.99。
- 其余消息使用角色专属加权意图词；接近的候选降低置信度并保留原因。
- 无明确意图交给产品经理澄清。
- 已有会话固定 Agent；切换角色要求新会话，避免角色和 Memory 漂移。

## 团队讨论

AI 对齐室的 `TEAM` 会话按产品经理、架构师、测试工程师、运营分析师、项目经理顺序运行。每位员工使用自身已发布 Prompt、模型和并发上限，并读取本轮前序发言；最后一位项目经理输出统一执行方案。每条消息记录实际 `agent_id` 与讨论阶段，供应商 usage 也分别归属对应 Agent。

团队讨论用于方案评审，不推断或执行任何写工具。整轮使用唯一请求 ID 和一次预扣；模型失败、连接取消或上下文失效时通过 `agent_runs` 幂等退款。成功后的最终方案写入项目 Memory，供后续单人对话与工作流读取。

## AI 原型协作

原型生成冻结产品经理、架构师和测试工程师的 Prompt、模型、版本与并发配置。产品经理先定义目标用户、成功条件和 2-5 条可执行用户旅程；架构师只输出受 Pydantic 约束的安全 DSL，将每一步绑定到真实页面、按钮或链接及预期页面；测试工程师独立检查旅程真实性、边界状态、表单可访问性、移动端和验收风险。无效结构进入有界返修，确定性门禁会补齐缺失页面的安全体验路径，但不会执行模型生成的 HTML 或 JavaScript。

新 DSL 把 `journeys` 作为必填合同，并验证步骤连续性、控件可执行性和导航目标。历史版本缺少该字段时仍可读取为空路径；重新生成或质量修复后升级为新合同。原型工作室可按结构化动作事件引导体验、突出当前控件并报告错误操作，批准后的物化流程把页面任务、单页用例和端到端旅程用例一并写入交付证据。

## 工具

8 个默认角色通过 Tool Registry 使用 `context_search`、`knowledge_search`、`task_create`、`requirement_create`、`report_generate`、`notification_create`、`meeting_summary`、`architecture_generate`、`testcase_create`、`analytics_report`。

运行时允许集合 = 代码角色硬白名单 ∩ 数据库启用白名单 ∩ 用户角色。数据库存在配置时，空集合表示全部禁用，不会回退到 Agent 声明。读取项目上下文可自动执行；写任务、报告、通知等工具必须命中明确动作意图。工具名称和资源 ID 写入审计日志，不复制聊天正文。

`knowledge_access=false` 会在运行时移除 `knowledge_search`，不能只靠 Prompt 约束。用户还必须拥有 `agents:read`；涉及项目写入时叠加 `projects:write` 和项目成员角色。

## 人工审批

- 产品经理、项目经理、架构师、会议纪要员和通知秘书默认开启人工确认，可由管理员逐 Agent 调整。
- 当前聊天中的 `task_create` 在执行前写入 `agent_actions`，相同会话和输入复用同一条待审批记录。
- 批准使用数据库行锁；执行前重新检查发起者状态、项目写权限、代码硬白名单和数据库工具权限。
- 已执行或已拒绝动作不能再次决策；审批和拒绝均写入审计日志。

## 并发与幂等

- 每个 Agent 配置 `concurrency_limit`，API 和 StateGraph 节点统一申请执行槽位。
- PostgreSQL/Redis 部署使用带过期时间的 Redis Sorted Set 租约，支持多 Uvicorn 实例；活跃租约会周期续期，异常和断连在 `finally` 释放，进程崩溃由租约过期恢复。
- Redis 不可用时退化到按 Agent 隔离的进程内动态限流器，运行中修改并发上限仍会立即生效；降级模式保持单实例正确性，但不承诺跨实例限流。
- 每次聊天创建唯一 `agent_runs.request_id`，重复请求不会重复推理或扣费。

## 多 Agent 交接与事务边界

- 工作流创建时按发起者角色冻结参与 Agent 的 Prompt、模型、版本、启用工具、知识权限和并发限制；一次运行不会混用不同配置版本或在权限变更后静默漂移。
- Requirement 节点先让产品经理生成严格结构化需求合同，服务端为 2-10 项验收标准分配稳定 `AC-xx` 标识，并在模型输出无效时生成包含原始目标的确定性基线，不再把固定的平台功能模板冒充用户需求。架构师与测试工程师并行且彼此不可见地审查可行性与可验收性；`ACCEPT` 不能携带问题，`CHALLENGE` 必须包含具体关注或修改建议，无效输出记为 `ABSTAIN`。存在合法质疑时产品经理只可修订一次，重复指纹或无效合同不替换原稿；修订后重新收集两份评审，最终仍被质疑则复用 `plan_review` 人工门禁。
- 启动弹窗使用只读预检展示同一能力政策下的团队就绪状态及同项目 Team Performance Profile，不扣费也不创建运行。运行入口会重新生成 Agent 与绩效快照并复用同一预检函数，在计费和入队前阻断能力不足；通过后的同一份快照继续用于 Planner、计划审批和实际分支，避免检查与执行漂移。
- Planner 只接收冻结快照中至少有一个可用专业工具且并发额度有效的专业角色。角色固有能力与工具能力组成可选择目录；知识检索同时要求知识权限和检索工具。计划必须声明每个分支的所需能力、组队依据和至少一个 `criterion_ids`，服务端在解析、人工批准和实际调度前验证所需能力是对应角色能力的子集、引用的 AC 属于当前需求合同、所有 AC 至少由一个分支负责，并验证整份计划覆盖用户明确要求的知识检索或通知投递能力。少于两个合格角色或明确能力不可用时不调用模型或启动分支，不以通用计划替代原需求。
- Planner 在交付完整性、风险控制和并行效率三个相互隔离的上下文中独立生成候选。代码先隔离非法候选，再按能力覆盖、角色匹配、成功标准、并行效率和交付防线形成 100 分证据；冻结的同项目历史必须与当前 Agent ID、Prompt、模型、工具、权限和并发配置完全一致，且分支结果会由重试、修订和质量失败信号校准。只有当前配置样本充足的角色生成 `-5..+5` 可靠性调整，旧配置样本仅保留排除计数，不改变结构分、能力合同或必需角色。架构师只能从合法候选 ID 中仲裁，异常输出按承诺状态、调整后决策分、结构分和稳定 ID 降级。完整候选、绩效证据、结构指纹、选择依据和少数意见随版本保存，选择历史版本时与计划一起切换。
- Team Performance Profile 同时保留角色聚合和能力上下文聚合。角色聚合继续服务启动预检；候选的可靠性、成本和关键路径只读取 `required_capabilities` 规范化集合完全相同的上下文。缺失能力元数据的历史只进入角色聚合，没有精确上下文时返回显式 `NONE` 且不回退；每个角色最多冻结 10 个按样本量和能力签名稳定排序的上下文。
- 每个候选的实际专业角色在仲裁前独立签署执行承诺，只能审查自己的任务、依赖、冻结能力和交付边界。合法 `ACCEPT` 不得携带阻塞项；`CHALLENGE` 必须给出缺失输入、依赖风险或修改建议；无效输出记为 `ABSTAIN`。三个独立候选都未就绪且至少存在一份合法质疑时，服务端确定性选择最接近就绪的候选，只允许 Planner 进行一次结构不同的协商修复，并只对修复候选重新收集承诺。存在 `READY` 候选时架构师和确定性降级都只能选择 `READY` 候选；修复无效、重复或仍未闭环时服务端把计划审批改为强制门禁。
- 专家节点读取前序节点的真实文档产物，而不是只读取静态占位数据；最终报告汇总完整产物链。
- 专业分支的确定性错误或局部重试耗尽会在已提交波次检查点进入人工恢复门禁；操作员可携带修复指令只重跑失败角色及下游，或清空旧分支产物退回 Planner，成功 Handoff 不会被无故重复执行。
- 新生成的专业 Handoff 由服务端封存计划版本、修订轮次、规范化输入、输出、证据上下文和直接上游输出的 SHA-256 指纹。证据上下文包含分支负责的当前 AC 定义、PRD/系统设计内容哈希和直接上游输出指纹；Quality Gate 按 DAG 重新计算整条链，被修改的交接、失效的证据上下文或仍引用旧上游指纹的下游会被确定性送回返修。没有封存字段的历史快照继续按旧合同读取。
- Handoff v3 不接受靠长度或自由文本来源通过：专业 Agent 除有界的 `summary`、`decisions`、`evidence`、`risks`、`open_questions` 和 `next_actions` 外，每条 evidence 必须声明非空 `criterion_ids` 和 `source_refs`。证据必须合计完整覆盖 assignment 负责的 AC，且来源只能引用当前 `artifact:PRD`、`artifact:SYSTEM_DESIGN` 或 `handoff:<direct_upstream_role>`；风险、问题和行动的 `owner_role` 仍只能来自当前执行计划。服务端生成可读正文，并将原始字段、正文和证据上下文共同封存；篡改任一结构化字段或权威来源都会使证据链失效。下游 Agent 只接收结构化投影，解析失败原文保留在受控快照用于诊断但不继续传播。v1 自由文本与 v2 结构化历史 Handoff 仍可读取和参与兼容门禁。
- 测试、运营和架构三个 Reviewer 在彼此不可见结论的前提下并行评审 Handoff。至少两份合法结构化合同构成 quorum；仲裁使用有效评分中位数与多数票，同时保留少数意见。确定性门禁、任一开放阻塞冲突或阻塞问题都拥有否决权；单个 Reviewer 调用失败或合同无效时弃权，低于 quorum 时质量节点按 worker 策略重试而不会静默放行。代码过滤计划外角色并定向推导返修角色，模型自报高分不能绕过。
- 只读推理结果进入 `state_json`，有副作用的任务和报告写入必须通过持久化 Saga 步骤执行。
- 回滚由代码注册的补偿器和合法状态机决定，模型不能临时编造撤销动作。
- 终态失败或取消会逆序补偿；补偿对象被人工修改时停止自动处理，锁定该项目的后续工作流并进入人工核对。

## Token 计费

平台采用固定产品额度预扣，同时将供应商返回的 input/output token、模型、耗时和按配置费率估算的成本写入 `llm_usage`。供应商不返回 usage 时明确标记为 `estimated`。余额通过数据库条件 `UPDATE` 原子扣减；执行失败生成唯一退款流水，重复失败回调不会重复退款。

## 反馈与评测

助手消息支持点赞、点踩和保留原回答的重新生成；重新生成不再次执行写工具，并记录原消息关联。管理员可维护跨角色评测用例、必需/禁用证据、Rubric、阈值和权重。每次运行冻结测试集 revision 与 Agent Prompt/模型版本；Challenger 运行会用指定草稿替换目标 Agent 快照，并冻结目标 Agent、候选版本和预期生产版本。异步 worker 按需求覆盖、正确性、相关性、完整性和安全性评分；平均分回退、逐案例回退、Judge 降级或安全失败都会阻断发布。无外部模型时明确使用确定性评分，配置外部 Judge 后若 Judge 失败则不得放行。页面与 `python -m app.evaluation run` 均保留逐案例回答、证据、维度分数、延迟、错误和门禁结论。

团队测试集必须覆盖当前已配置的产品经理、架构师、测试工程师、运营分析师和项目经理核心角色；辅助角色在发布自身 Challenger 时仍必须至少有一个对应角色用例。覆盖契约在运行入队、worker 终态和 Challenger 发布前分别校验，新增核心 Agent 或归档用例不能复用历史绿灯绕过门禁。评测实验室显示权威覆盖状态和缺失角色，并可并发安全地为缺失角色生成可编辑的基础用例；已有自定义用例不会被覆盖，重复调用不会重复创建。

当前仍为点踩的生产回答会进入仅管理员可见的反馈队列；点赞和已改回正向的反馈不会进入。管理员可忽略候选项，或将其转为启用的回归用例。转化事务冻结用户输入、Agent 回答、评论、Agent 身份与角色，后续源消息修改不影响证据；同一反馈最多生成一个用例，`request_id` 保证转化和忽略幂等。审计日志只保存反馈、用例、Agent 和角色标识，不复制输入、回答或评论正文。

反馈响应先把用户身份伪匿名化，并统一替换邮箱、手机号、证件号、银行卡、IP、Bearer/API 密钥等敏感值。原始正文只留在受控冻结证据中；新建、编辑和由反馈转化的评测输入均使用脱敏文本，避免后续 Agent、Judge 或 Prompt 优化链再次传播生产个人信息与凭据。有效负反馈按 Agent 角色与脱敏后的共同信号形成 `Failure Cluster`，已忽略项不参与；`Regression Coverage` 独立于核心角色覆盖，优先使用来源反馈关联的启用用例，再以同角色启用用例的相似度区分已覆盖、部分覆盖和覆盖缺口。评测实验室可展开脱敏代表样本，并从缺口进入现有回归用例创建流程。

门禁失败证据可以进入持久化 Prompt 调优队列。一次任务只接受同一 Agent、同一冻结版本的可调优结果；除了案例失败、回退和执行错误，案例虽通过自身阈值但低于发布均分阈值或触发安全硬门禁时也可进入。Optimizer Agent 从冻结输入、回答、维度分数和 Judge 依据生成通用行为改进，独立 Reviewer Agent 不读取 Optimizer 的内部 rationale，只审查原 Prompt、提案和失败证据。Reviewer 必须同时通过角色对齐、提示注入、工具范围、评测迎合和治理边界检查；代码侧还会阻断越权/绕过模式及把多个冻结缺失关键词原样写入 Prompt 的测试迎合。拒绝意见和确定性失败类别会在有界轮次内回传给 Optimizer 返修；达到上限仍未通过时任务进入 `REJECTED`，不会创建版本。

调优任务使用 request hash 幂等、PostgreSQL 队列认领、续租心跳、fencing token、指数退避、取消、手动重试和短事务 checkpoint。每轮 Optimizer/Reviewer 调用期间不持有数据库事务，逐轮摘要和提案指纹支持中断恢复；`REJECTED` 不会自动重试，但管理员可以基于同一冻结证据重新入队。双门禁通过后只复制冻结 Agent 配置并替换 `system_prompt`，创建新的 `DRAFT`；任务不会直接发布或修改生产 Agent，管理员仍需选择匹配当前生产版本的基线并完成 Challenger 评测。审计只记录运行、结果、Agent、版本和证据指纹，不复制 Prompt、回答、Rubric 或 Reviewer 正文。

发布时再次校验运行已完成、门禁通过、基线与测试集一致、草稿仍匹配冻结证据，并用预期生产版本执行乐观并发检查。发布记录和版本激活在同一事务中写入；`request_id` 保证幂等。回滚只允许作用于仍是当前生产版本的评测发布，创建新的恢复版本并在原发布记录上保留发布者、回滚者、时间和版本链。审计与通知只包含 Agent、运行和版本标识，不包含 Prompt 正文。

## Memory

- 短期：最近 20 条中按 12,000 字符预算截取。
- 用户偏好：Redis。
- 项目：PostgreSQL，普通记忆固定窗口，旧内容合并为每个项目/Agent 唯一滚动摘要，摘要最大 4,000 字符。
